## Reading the table

- The component matters if switching it off lowers accuracy by more than one or two queries, or moves failures into its class (no critic → hallucination, no JSON retry or no constrained decoding → tool-call error).
- Band, score, checklist and approvers come from the tools in every configuration, so full reviews mostly pass whatever is switched off; the differences show on questions.

## Team notes

Each configuration was run once on the 30-question dev split, so one query is 3.3 points and a one-query difference is noise.

The reranker hurts, which confirms D38. Turning on the MiniLM reranker over the top 12 candidates lowered accuracy by 0.10 (3 reasoning errors). Fact recall fell to 0.84, citation precision to 0.65, and p95 latency rose from 10.8 s to 27 s. It reorders policy passages for these vendor-specific questions in a way that pushes the passage the answer needs further down. Hybrid retrieval without a reranker stays the default.

The critic and JSON retry never triggered on dev. Switching either off gave the same results as the full agent, down to the same tokens (3,515 median). With constrained decoding, every reply was valid JSON on the first try (100%) and the critic found nothing to replan. They are safety nets, so we keep them: they cost nothing when unused and protect against a different model or a backend without json_schema (the fallback to json_object exists for that case).

Constrained decoding did not change accuracy on dev. With JSON mode only, accuracy was 1.0 and completion 100%, with no tool-call errors. JSON first try was 100% with constrained decoding and median tokens were 3,515. The repair and retry step (D32) covered any malformed replies, so the end result was the same. We keep json_schema as the default for two reasons. First, it removes a failure class instead of fixing it afterwards. Second, it matters more on harder inputs and longer outputs than dev has. On dev, JSON mode plus repair is enough.. If accuracy or JSON-first-try drops and the failures move into tool-call errors, D32 is confirmed. If not, JSON mode plus the repair step is enough on dev.

The key-facts and citation-limit fixes do not explain the gain one at a time. Each one switched off still scored 1.0. The citation precision values (0.83 and 0.85, against 0.81 for the full agent) are within noise. The step up from the Week 3 agent (0.933 accuracy, 0.65 citation precision) comes from the D40 fixes together. The likely reasons are that they cover for each other, that the two fixes without a switch (named source first, drafts excluded) do most of the work, or run-to-run variation, which the 4.1 benchmark measures.
Limitation: ceiling effect. The full agent scores 30/30 on dev, so removing a component can only show up as a drop, and dev has too few hard questions to cause one. Ablations on a fresh, harder set would discriminate better. We did not tune on test (D12), and eval_v1 stays frozen. A held-out eval_v2 of harder questions (multiple vendors, superseded policies, conflicting evidence) is proposed future work.

Conclusion. Only the reranker made a measurable difference, and a negative one. It stays off, which confirms D38. Every other component can be removed alone without a loss on dev. So on this split the agent’s accuracy comes from the deterministic tools and the D40 fixes together, not from any single safeguard. We keep constrained decoding, the critic and JSON retry: they cost nothing when they aren’t needed and guard against harder inputs or a different backend. The ceiling effect means dev can’t rank them further. That is a stated limitation, and a harder held-out eval_v2 is future work.
